# 非对局 UI 分阶段改进方案

状态：阶段 1 已实施并完成专项验证，尚未提交；阶段 2–5 未开始。

目标：先接通导航、教程和邀请流程，再统一大厅与设置页布局，让新用户能够找到入口、理解操作结果，并在失败后继续完成任务。

依据：2026-11-15 非对局 UI 只读评估，以及用户明确的实施顺序。此前登录后画面使用隔离浏览器模拟响应，真实联机和生产环境仍需在实施时验证。

技术基础：沿用 React、React Router、Tailwind、现有 UI 组件及主题令牌。

## 范围与决策

- 覆盖首页、大厅、房间等待页、邀请入口、独立教程、设置、资料、关于及相关错误状态。
- 游戏主界面不动：不修改牌桌、手牌、座位、游戏内导航、游戏内说明书、对局运行器、游戏规则及回放画布。
- `/local` 保留原来的存档提示、人数选择和开局流程；本轮仅将教程入口正确指向它，不重新设计该页面。
- 保留现有主题、字体和素材。先改善信息结构与交互，不增加新皮肤、装饰动画或大型首页视觉工程。
- 公共导航仅装配到明确列出的非对局页面；不在所有路由共同的根节点直接追加导航。
- 布局样式限于非对局页面。避免修改全局主题令牌及对局共用组件的默认外观；必要的差异通过页面级组合或参数表达。
- 本轮不新增独立角色图鉴、交互教学引擎或账号系统。教程末尾使用已有目的地。
- 仅规划有明确用户收益的改动，不进行邻近代码清理、框架迁移或新增依赖。
- 后续实施每阶段独立验收；未经用户明确授权，不自动创建 Git 提交。

## 阶段总览

| 阶段 | 优先级 | 交付内容                     | 完成条件                                           |
| ---- | ------ | ---------------------------- | -------------------------------------------------- |
| 1    | P1     | 公共导航与返回路径           | 主要辅助页面可发现、可返回，游戏页面不出现新增导航 |
| 2    | P1     | 教程行为与内容修正           | 每个按钮兑现名称，跳过与完成区别明确               |
| 3    | P1     | 邀请与身份衔接、房间失败恢复 | 新老用户可沿原邀请进入房间，失败有明确出口         |
| 4    | P2     | 大厅与设置统一布局           | 相同页面骨架、清楚的任务顺序、桌面与手机均可用     |
| 5    | 验收   | 跨页面与生产版本回归         | 关键路径、所有现有主题及对局边界通过检查           |

阶段 1 → 2 → 3 → 4 → 5 顺序推进。前三阶段不等待视觉重排，每阶段均应独立交付可用结果；第五阶段进行整体验收。

## 阶段 1：补齐导航与返回路径

### 交互方案

1. 首页保留「单机练习」「多人房间」两个主入口，增加可见的「新手教程」入口；设置和关于放在次级导航中。
2. 大厅提供清楚的页面标题和轻量导航，能够进入教程、设置、关于及已登录用户资料。头像相关操作不占据主任务区域。
3. 桌面使用紧凑顶栏；手机保留页面标题、明确返回入口及一个带文字的菜单按钮。菜单可键盘操作，关闭后焦点回到触发按钮。
4. 设置、资料、关于使用一致的返回模式：从首页进入可返回首页，从大厅进入可返回大厅；直接打开地址时有确定的站内默认目的地，不仅依赖浏览器后退。
5. 房间等待页沿用明确的「离开房间」动作及原有离房逻辑，不添加会绕过该动作的首页链接。
6. 首页版权确认仍保留，将「继续教程」改为与当前入口相符的表述，不删除必要声明。

### 实施边界

- 拟新增一个供多个非对局页面复用的轻量页面框架，负责标题、导航、内容容器及返回入口。
- 主要涉及 `client/src/pages/Landing`、`Lobby`、`Settings`、`PlayerProfile`、`About` 和路由装配；版权措辞涉及 `client/src/lib/copyright.ts`。
- 房间页先只核对返回/离开语义，不进行视觉重排。

### 验收

- [x] 从首页可找到教程、设置和关于；从大厅可找到上述页面及自己的资料。
- [x] 手机端辅助目的地最多经一次菜单展开即可看到；当前页面有明确标识。
- [x] 设置、资料、关于直接访问时也有可用返回入口。
- [x] 键盘能打开、遍历、关闭导航；焦点可见，不落到被遮挡内容。
- [x] 公共框架仅装配到五个非对局路由；对局、单机及回放的原有路由结构不变，自动检查未发现新增公共导航。

### 阶段 1 实施记录

- 新增 `SiteLayout` 和 `useSiteReturnTo`，辅助页保留首页/大厅入口，刷新后仍能返回；独立教程仅调整关闭及完成页返回目的地。
- 手机菜单沿用现有 Sheet；提供当前页标识、键盘操作、焦点约束及关闭后的焦点恢复。
- 仅调整页面外层高度以容纳顶栏；大厅与设置内部布局保留，未修改游戏主界面、全局主题或共享 UI 默认样式。
- 新增 `e2e/tests/site-navigation.spec.ts`，先确认新增场景失败，再完成实现与回归。
- 实际直接调用本地 CLI（避免 pnpm 自动依赖安装）：客户端 `tsc --noEmit`、`eslint src/ ../e2e/tests/site-navigation.spec.ts`、`vitest run`、`vite build` 均通过；单元测试 147 个文件、2394 项通过，新增及相关文件 Prettier 检查通过。
- 生产预览执行 `site-navigation.spec.ts`，desktop-chrome、mobile-android、tablet-ipad 共 27 项通过；1440/768/390 宽度截图与尺寸检查未发现横向溢出。
- 扩展 Playwright 回归（导航、首页、设置、教程、版权、房间分享、固定对局）71 项通过、1 项失败：`fixture-match.spec.ts:48` 期待移动端 `unlock-response-bar`，实际为响应窗口。隔离导出的改动前 HEAD 同样在该断言失败；保留原游戏实现与原测试，另行处理。
- 构建仍有既有 coarse CSS 变体、包体积及 Vite 配置提示；本阶段未改相关来源。联机行为使用现有模拟夹具，未验证真实服务端或手机真机。

## 阶段 2：让教程的内容与操作一致

### 交互方案

1. 保留现有分步教程，先校正规则摘要和文案。人数与当前支持范围一致；其他规则说明逐条核对项目手册与现有实现。
2. 教程末尾提供「单机练习」「进入大厅」两个真实目的地。单机练习到 `/local`，由现有页面继续处理存档和人数选择，不自动开新局或覆盖存档。
3. 暂时移除独立教程中尚未接通的「浏览角色图鉴」选项。游戏内现有说明书不受影响。
4. 「跳过教学」返回进入教程前的首页或大厅，不显示「已掌握基础规则」。正常结束可显示「已读完基础介绍」，避免把阅读等同于掌握。
5. 保留进度与关闭操作，补充回看上一步的能力。新会话再次进入时，已完成用户可以明确选择重新阅读。
6. 仅在四层梦境、回合顺序等确实有助理解的步骤加入简短图示，复用现有素材。图示保持静态，不嵌入游戏运行器，不扩展成交互训练关卡。

### 实施边界

- 主要涉及 `client/src/pages/Tutorial/index.tsx`、`components/TutorialOverlay`、`stores/useTutorialStore.ts` 及 `shared/src/tutorial/scenarios/basics.ts`。
- 目的地跳转由教程页面处理，避免把网页路由塞进共享教程引擎。
- 若现有教程进度接口不支持回看，只增加所需进度行为并覆盖测试，不重写整个引擎。

### 验收

- [ ] 「单机练习」进入现有准备流程；有存档时仍显示原有继续/新局选择。
- [ ] 「进入大厅」到达大厅，且不会误触发建房或匹配。
- [ ] 跳过、关闭、正常完成有不同且准确的结果；均有确定返回位置。
- [ ] 上一步、下一步与进度展示一致，首尾不越界。
- [ ] 教程人数、关键规则、动作名称与实现一致；不再出现无对应目的地的按钮。
- [ ] 390px 宽度下正文和操作可读可点，较长步骤的滚动不遮挡操作。

## 阶段 3：接通邀请、身份与房间状态

### 目标流程

未登录：邀请链接 → 显示受邀房间码 → 设置昵称或恢复账号 → 必要的恢复码保存确认 → 加入原房间 → 房间等待页。

已登录：邀请链接 → 加入或附着原房间 → 房间等待页；已在房间或已有对局时沿用现有服务端状态与跳转规则。

### 交互方案

1. 用受邀房间码作为待继续的任务；只携带房间码，不设计通用任意 URL 跳转机制。通过地址参数保留，使昵称页刷新后仍知道要加入哪个房间。
2. 从 `/invite/:code` 或直接访问 `/room/:code` 进入的未登录用户，都走同一条衔接路径。
3. 昵称/恢复表单上显示「加入房间 ABC234」，让用户知道登录后会发生什么；可主动取消邀请并回普通大厅。
4. 创建身份或恢复账号产生新恢复码时，先展示并完成现有确认步骤，再自动继续入房，不让跳转卸载弹窗。
5. 身份初始化、账号恢复失败时保留房间码与用户输入，错误显示在当前表单旁。
6. 房间加载、加入中、成功和失败使用互斥状态。失败时结束「加载中」，展示原因与可执行动作。
7. 房间不存在、已满、禁止加入或已开局等情况按现有服务端返回能力分别解释；提供返回大厅/重新输入房间码。网络失败提供重试，不让用户把本地模拟成功误认为加入了朋友的真实房间。
8. 成功加入、主动取消后结束待处理邀请；后续普通登录不应再次加入旧房间。只使用现有加入接口，不另造加入链路。

### 实施边界

- 主要涉及 `client/src/pages/Invite/index.tsx`、`pages/Lobby/index.tsx`、`pages/Room/index.tsx` 与现有身份结果、房间请求衔接。
- 审查当前网络失败回落本地模拟的行为，仅在真实邀请流程所需范围内区分状态，不全面改造 API 层。
- 生产环境邀请链接先经过服务端。验收时同时检查服务端跳转和开发环境客户端跳转；保持分享卡片内容与既有接口协议。

### 验收矩阵

| 场景                           | 预期                                       |
| ------------------------------ | ------------------------------------------ |
| 新访客打开有效邀请             | 昵称页保留房间码；恢复码确认后进入目标房间 |
| 用恢复码恢复已有账号           | 确认新恢复码后进入原受邀房间               |
| 已登录用户打开邀请             | 进入目标房间，无额外昵称流程               |
| 在身份页面刷新                 | 邀请目标仍在，输入状态按现有表单约定处理   |
| 直接访问房间且未登录           | 登录后回原房间，不停留普通大厅             |
| 邀请格式无效、房间不存在或已满 | 显示明确错误和出口，不继续显示加载         |
| 网络中断后重试                 | 保留目标房间，成功后只呈现一次入房结果     |
| 取消邀请后正常访问大厅         | 不再次执行旧邀请                           |
| 生产分享链接                   | 经过真实服务端跳转后仍满足以上路径         |

## 阶段 4：统一大厅与设置的页面布局

### 统一规则

- 共用阶段 1 的页面框架、标题层级、外侧边距、内容起始线和表单间距。
- 桌面内容最大宽度初定 960px，平板流式布局，手机外边距 16–20px；具体尺寸以 1440/768/390 截图检查为准。
- 共同容器不意味着每个表单都要拉满：单个输入组保持合适宽度，页面内部按任务分栏。
- 使用现有颜色和字体；主要操作、次要操作、链接采用一致层级，禁用时保留可读性并解释必要原因。
- 移动端主要触控目标至少 44px；输入有标签，约束与错误就近展示。

### 大厅

1. 顶部只保留标题、紧凑账号入口，以及存在时的「回到对局」。头像随机更换归入设置，不占据大厅首屏。
2. 「加入房间」上移，房间码输入和提交在普通大厅手机首屏可见。
3. 桌面在统一容器中用两列组织加入/匹配与创建房间，公开房间列表位于其下；手机按加入、匹配、创建、公开房间顺序展示。
4. 创建房间默认突出人数和创建动作，赛制及公开性收纳为可展开的「房间选项」，收起时仍能看懂当前公开/私密状态与赛制摘要。
5. 公开房间保留筛选、刷新、人数及加入操作；明确加载、空态、失败和加载更多状态。
6. 请求中在被操作的位置显示「加入中」「创建中」等反馈；字段错误贴近字段，房间操作错误贴近对应区域。
7. 保留必要的指纹用途说明，但放在身份相关区域，不让它成为每次进入大厅的首要内容。

### 设置

1. 分组顺序为音效、外观与动效、账号、成就，优先呈现常用控制。
2. 桌面采用限宽设置行：左侧分组名称，右侧控件；手机改为单列，避免标签和值被推到两端。
3. 音效统一为清楚的「音效」开关及「音量」，当前开关状态可辨；静音时音量不可操作的状态明确。
4. 主题保留真实预览，但改为更紧凑的选择项，减少手机三排大图的高度；已选主题有清楚标记，键盘也能选择。
5. 外观、动效、音效均即时生效，不增加误导性的全页保存按钮；账号修改仍按现有请求与确认流程执行。
6. 恢复码重新生成保留独立的后果说明和二次确认。成就保留真实零数据与空态，不增加装饰性统计。
7. 共享主题选择器若被游戏内菜单使用，本阶段只调整设置页的组合方式或显式紧凑参数，默认游戏内表现保持不变。

### 验收

- [ ] 1440/768/390 下大厅与设置的外侧对齐、标题及内容起始位置一致，页面无横向溢出。
- [ ] 390×844 普通大厅首屏能看见并操作房间码输入与加入按钮；手机软键盘弹出后仍能完成提交。
- [ ] 桌面大厅利用两列空间，设置控件不横跨整块宽屏，手机阅读顺序正确。
- [ ] 设置页手机首屏可操作音效；主题列表不遮挡或挤压其他控制。
- [ ] 加入、创建、筛选、恢复码和主题等既有行为保留；匹配中禁用逻辑仍然正确。
- [ ] 五种现有主题下文字、输入、按钮、焦点和错误状态清晰。

## 阶段 5：验证、复核与交付

### 实施阶段的验证方式

- 行为修复先写能复现问题的测试，确认失败后最小实现；覆盖用户可见结果，不重复测试组件内部写法。
- 优先扩展现有测试：`e2e/tests/landing.spec.ts`、`tutorial.spec.ts`、`settings.spec.ts`、`room-share.spec.ts`、`friend-room-flow.spec.ts`，以及 `tests-online/recovery-code.spec.ts`。
- 邀请码保留、教程进度边界等逻辑使用定向单元测试；纯布局变化主要用截图和交互验收，不为 className 写镜像测试。
- 本地模拟仅验证布局和可控错误；邀请及恢复码衔接必须补真实本地后端验收。
- 在生产构建上复核最终页面，不能只用 Vite 开发服务器宣布通过。
- 自动设计检查作为提示，人工区分主题预览、选中环等合理场景，不机械删除产品已有设计。

### 计划执行的检查命令

以下为各阶段的标准命令入口；阶段 1 实际执行结果见上方实施记录，其余阶段尚未执行。工作目录为仓库的 `game/`。

- `pnpm --filter @icgame/client typecheck`
- `pnpm --filter @icgame/client lint`
- `pnpm --filter @icgame/client test`（按改动范围先运行定向用例）
- `pnpm --filter @icgame/shared test`（仅教程共享逻辑发生变更时）
- `pnpm --filter @icgame/e2e test`（按阶段先筛选上述相关文件）
- `pnpm --filter @icgame/e2e test:online`（需要既有联机测试环境）
- `pnpm --filter @icgame/client build`，之后在生产预览上检查截图与关键路径。
- `git diff --check`，并复核改动清单、共享组件影响和对局页面回归结果。

### 总体验收路径

- 首页 → 教程 → 单机准备页；首页 → 大厅 → 加入或创建 → 房间等待页。
- 邀请 → 新身份/恢复账号 → 恢复码确认 → 原受邀房间。
- 首页/大厅 → 设置 → 修改偏好 → 返回原入口。
- 房间异常 → 看懂原因 → 重试或返回大厅。
- 桌面、平板、手机以及全部现有主题分别检查；真机重点检查昵称、恢复码、房间码输入时的软键盘遮挡。
- 对局与回放只做回归观察：没有新增公共导航，牌桌布局、交互和共享组件默认表现无变化。

## 本轮暂不包含

- 首页品牌视觉重做、大量插画或动画。
- 独立角色图鉴、完整交互教学关卡。
- 关于页的大幅内容扩展、资料页新增统计或成就体系重做。
- 房间等待页整体重设计、对局界面或游戏规则变化。
